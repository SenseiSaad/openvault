# Deploy — new AWS stack (`infra/`)

This is the runbook for the ECS/Fargate stack. It is **not** the live
Amplify/Render deployment. Do not point this stack at
`openvault.saadops.site` until you are deliberately migrating users.

> **Status:** Terraform has been formatted/validated/planned only in this
> repository. No `apply` has been run, and no billable resource has been
> created. The steps below are the first-apply procedure.

## 0. What you need before starting

| Input | Example | Where it goes |
|---|---|---|
| AWS account + admin credentials for the first apply | `<account-id>` | local `AWS_PROFILE`; not GitHub |
| Parent domain and a **new** subdomain | `v2.example.com` | `TF_VAR_domain` / GitHub `DOMAIN_PROD` |
| Route 53 parent delegation | paste NS records into parent DNS | after first zone apply |
| Alert email | `you@example.com` | `TF_VAR_alert_email` / GitHub `ALERT_EMAIL` |
| Bedrock model + inference-profile ARNs | `arn:aws:bedrock:ap-south-1:<acct>:inference-profile/in.anthropic...` | `TF_VAR_bedrock_model_arns` / `BEDROCK_MODEL_ARNS` |
| GitHub owner/repo | `owner/openvault` | `OIDC_ALLOWED_SUBJECTS` |
| SES production access | requested in console | `EMAIL_HOST_*` SMTP creds |
| RDS master password | generated by RDS in Secrets Manager | build `DATABASE_URL` |

The first apply is done **locally with a human admin/`PowerUserAccess`+IAM
identity**, because the GitHub OIDC roles do not exist yet. After that, use the
protected `terraform-apply` workflow. Never put AWS access keys in GitHub.

Prerequisites: Terraform `>= 1.9`, AWS CLI v2, Docker, `jq`, `python3`, and a
running `gitleaks` only for local checks.

## 1. Bootstrap remote state (once per account)

```bash
cd infra/bootstrap
terraform init
terraform plan
terraform apply        # creates openvault-tfstate + openvault-tf-locks
```

If `openvault-tfstate` is already taken globally, change `name_prefix` **and**
the bucket name in `infra/envs/*/backend.tf` before applying. Do not create a
second state bucket for staging; both environments use separate keys in the
same bucket.

## 2. First production/staging apply

Set variables without committing secrets:

```bash
cd infra/envs/prod
cp terraform.tfvars.example terraform.tfvars   # gitignored
$EDITOR terraform.tfvars
terraform init
terraform plan -out=tfplan
terraform apply tfplan
```

For the very first apply, the ACM certificate cannot validate until the
subdomain is delegated. Either:

* **preferred:** create the zone first, delegate, then run the full apply:
  ```bash
  terraform apply -target=module.dns_tls.aws_route53_zone.this
  terraform output name_servers
  # Paste those four NS values into the parent DNS provider for v2.example.com.
  # Wait for `dig NS v2.example.com` to show them, then:
  terraform apply
  ```
* or run the full apply and paste the NS records while ACM validation is
  waiting (the apply will pause; do not cancel it).

Do the same for staging with a separate subdomain. Staging is intentionally
cheap/destroyable; see `infra/envs/staging/main.tf`.

If the first apply creates ECS services before any image exists, the services
will be unhealthy but the apply still succeeds. Push the bootstrap image
(section 5) and they will converge.

## 3. DNS, SES, and Bedrock checks (manual)

1. **DNS:** `dig +short NS v2.example.com` returns the four Route 53 NS
   records. `dig +short v2.example.com` eventually returns the ALB.
2. **SES:** confirm the domain identity is verified (Terraform creates DKIM,
   SPF, DMARC, and the verification TXT). **Request production access** in the
   SES console; sandbox mode only sends to verified addresses. Create an SMTP
   user in IAM (SES SMTP credentials are not Terraform-managed) and save the
   username/password for section 4.
3. **Bedrock:** in the Bedrock console, request/enable the Claude Haiku 4.5
   model for `ap-south-1` and copy the **inference-profile ARN** (`in.` prefix).
   Set `bedrock_model_arns` to exactly the chat profile and the Titan embedding
   model. Model access and `ap-south-1` availability are **UNVERIFIED** until
   you see them in your account.
4. **SNS:** confirm the email subscription sent to `alert_email`; an
   unconfirmed subscription receives no alarms.
5. **Budgets:** AWS Budgets notifications are created by Terraform; confirm the
   email recipients in the Billing console.

## 4. Push application secrets to SSM

```bash
cp .env.production.example .env.production   # gitignored
$EDITOR .env.production

# RDS endpoint + managed password (do not paste these into chat/logs)
cd infra/envs/prod
terraform output -raw db_endpoint
terraform output -raw db_master_secret_arn

# Build DATABASE_URL with sslmode=require, then:
cd ../../..
./scripts/check_env.sh prod
./scripts/push_env_to_ssm.sh prod
```

For staging, create `.env.staging` from the template (gitignored), then run
`ENV_FILE=.env.staging ./scripts/check_env.sh staging` and
`ENV_FILE=.env.staging ./scripts/push_env_to_ssm.sh staging`.

`BOOTSTRAP_PLATFORM_ADMIN_*` are read once by the `migrate` task. After the
first successful login, remove both from `.env.production`, delete the SSM
parameters, and remove them from `app_secrets` in Terraform (then apply) so they
are no longer injected on every task launch.

## 5. First images and deploy

Build/push a bootstrap image so ECS can pull something:

```bash
AWS_REGION=ap-south-1
ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"
REGISTRY="${ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"
aws ecr get-login-password --region "$AWS_REGION" | docker login --username AWS --password-stdin "$REGISTRY"

docker build -f backend/Dockerfile -t "$REGISTRY/openvault-prod-api:bootstrap" .
docker build -f frontend/Dockerfile --build-arg NEXT_PUBLIC_API_URL= \
  -t "$REGISTRY/openvault-prod-web:bootstrap" .
docker push "$REGISTRY/openvault-prod-api:bootstrap"
docker push "$REGISTRY/openvault-prod-web:bootstrap"
```

Then either run the deploy script locally (configured with the same role/env), or
finish GitHub setup and push `main`. The deploy script runs migrations, updates
all three services, waits, and smoke-tests:

```bash
ECR_REGISTRY="$REGISTRY" ECS_CLUSTER=openvault-prod-cluster \
PUBLIC_BASE_URL="https://v2.example.com" \
./scripts/deploy_ecs.sh prod bootstrap
```

## 6. GitHub OIDC, environments, and variables

1. Merge the `infra` branch to `main` only after the first apply created the
   OIDC provider and roles.
2. Run:
   ```bash
   gh auth login
   ./scripts/setup_github.sh
   ```
   It creates `staging` and `production` environments (production requires your
   review), protects `main`, and protects `v*` tags. It never writes AWS keys.
3. Set repository **variables** (Settings → Secrets and variables → Actions →
   Variables). Required names:
   `AWS_REGION`, `AWS_BUILD_ROLE_ARN`, `AWS_DEPLOY_ROLE_ARN`,
   `AWS_DEPLOY_ROLE_ARN_STAGING`, `AWS_TERRAFORM_PLAN_ROLE_ARN`,
   `AWS_TERRAFORM_APPLY_ROLE_ARN`, `DOMAIN_PROD`, `DOMAIN_STAGING`,
   `ALERT_EMAIL`, `PUBLIC_BASE_URL_PROD`, `PUBLIC_BASE_URL_STAGING`,
   `ECS_CLUSTER_STAGING`, `ECR_REGISTRY`, `BEDROCK_MODEL_ARNS`,
   `OIDC_ALLOWED_SUBJECTS`, `DMARC_RECORD` (optional).
   `deploy.yml` can infer the ECR repository names from the defaults; set
   `ECR_API_REPOSITORY_*` / `ECR_WEB_REPOSITORY_*` only if you renamed them.
4. Set **environment secrets** `SMOKE_TEST_EMAIL` and `SMOKE_TEST_PASSWORD` in
   both `staging` and `production`. Use a dedicated, non-admin smoke account;
   production smoke fails if the account cannot authenticate.
5. Get the role ARNs from Terraform:
   ```bash
   terraform -chdir=infra/envs/prod output build_role_arn
   terraform -chdir=infra/envs/prod output deploy_role_arn
   terraform -chdir=infra/envs/prod output terraform_plan_role_arn
   terraform -chdir=infra/envs/prod output terraform_apply_role_arn
   ```

The build role can push only ECR images. The deploy role can update ECS, read
logs/SSM, and retarget the nightly backup. The plan role is read-only. The apply
role is broader and sits behind the required-reviewer `production` environment.

## 7. Normal delivery

* Open a PR touching `infra/**` → `terraform-plan.yml` posts a read-only plan.
* Every PR → `ci.yml`: backend tests + coverage, frontend tests/build, Docker
  build + Trivy, gitleaks, Terraform fmt/validate/tflint/checkov.
* Merge to `main` → `deploy.yml`:
  1. build once, push the same SHA to `openvault-prod-*` and `openvault-stg-*`;
  2. deploy staging automatically;
  3. wait for the `production` environment approval;
  4. run the migration task, update api/worker/web, wait, smoke test.

Production smoke uses `REQUIRE_AUTH_SMOKE=1` and fails without valid
`SMOKE_TEST_*` credentials.

## 8. Verify a deployment

```bash
curl -fsS https://v2.example.com/api/health | jq
curl -fsS https://v2.example.com/api/health/live
BASE_URL=https://v2.example.com REQUIRE_AUTH_SMOKE=1 ./scripts/smoke_test.sh
```

Then check CloudWatch `/openvault/prod/api` for `llm_usage` lines without prompt
content, confirm `/api/llm-status`, upload/download one document, and ask one
question. For Bedrock specifically, run `python manage.py check_bedrock` in an
API task (one tiny invoke unless `--no-invoke`).

## 9. Rollback / teardown

* Bad deploy: Actions → **Rollback**, previous SHA, production environment.
  This skips migrations and restores task definitions. See
  `docs/runbooks/bad-deploy-rollback.md`.
* Bad Terraform change: revert the commit, run the **Terraform apply** workflow,
  and verify the plan before approving.
* Staging teardown (only when not testing):
  ```bash
  cd infra/envs/staging
  terraform destroy   # stage-only: deletion protection/final snapshot disabled
  ```
  Production destroy is intentionally not documented as a one-liner; it has
  deletion protection and final snapshots, and should be a planned migration.

## 10. Common first-apply failures

| Symptom | Cause | Fix |
|---|---|---|
| ACM validation hangs | NS not delegated yet | Paste the zone NS records; do not cancel |
| ECS task `CannotPullContainerError` | No bootstrap image or wrong tag | Push `bootstrap`; check ECR repo/region |
| `ResourceInitializationError` | SSM parameter missing or execution role cannot decrypt | Push secrets; check `/openvault/<env>/*` and KMS |
| API starts then dies on health | DB/Redis/S3 unreachable | Check SGs, `DATABASE_URL`, bucket env; read `/openvault/<env>/api` |
| Migration task fails | Bad `DATABASE_URL` / RDS not ready | Fix SSM value; re-run deploy (services not updated) |
| SNS emails never arrive | Subscription unconfirmed | Confirm in the email inbox |
| Terraform apply role denied | Custom IAM policy missing an action | Add the project-scoped action; do not switch to AdministratorAccess |
